# CivicPulse Dhaka

CivicPulse is an independent complaint management app for a Dhaka pilot area. Citizens can register, submit reports, follow cases, and review completed work. Administrators verify and assign reports. Assigned department staff record progress. The super administrator creates and disables administrator and staff accounts. The app does **not** automatically send complaints to Dhaka city authorities.

## Public site

The permanent site is [civicpulse-dhaka.civicpulse-desktop.workers.dev](https://civicpulse-dhaka.civicpulse-desktop.workers.dev/). It is hosted on Cloudflare Workers with a shared SQLite backed Durable Object. The owner's live account and existing live data are preserved when the site is redeployed.

Share that link with citizens. They create their own citizen accounts and submit reports. After signing in as the owner, open **Administration** to create administrator and department staff accounts or disable their access. Disabled accounts lose their active sessions and cannot sign in until the owner reactivates them. Only the original owner account has the super administrator role.

The first dashboard visit shows a three-tip guide for that account's role. The user can dismiss it or reopen it with **Help** in the top bar. The guide is stored on that device and does not send training activity to the server.

Every signed-in user can open **Account security** to change their password. Changing it signs out that account's other sessions. Staff should change the temporary password given by the owner after their first login.

The code supports email verification and one-time password recovery links. They are **inactive on the current public site** because no verified sending domain or email provider has been configured. When email delivery is enabled, new citizens receive a verification link and cannot submit a complaint until verifying; existing accounts can request a link in Account security. Password reset links expire after 30 minutes and invalidate existing sessions. Until then, do not treat any stored email address as verified. Cloudflare Turnstile is enabled on public citizen registration and report submission, with server-side token validation and the existing request rate limits.

**Recovery codes work without email.** Every signed-in role can open Account security, enter the current password, and generate a 43-character one-time recovery code. Save it privately; the site displays it only once. If a password is lost, select **Use recovery code** on the sign-in page. A code is valid for one year, can be used once, and signs out other sessions when used. Generating a new code or changing the account password cancels the old code. Someone who loses both the password and the code cannot recover through the app until email delivery is configured; the owner should not guess identity from an unverified email address.

Administrators and the super administrator can enable **Authenticator sign-in** in Account security. Enter the current password, add the displayed setup key to an authenticator app, and confirm a six-digit code. Future sign-ins require both the password and a fresh code; a code cannot be reused. The secret is encrypted with a key derived from the account password in the database. Changing the password keeps authenticator sign-in active. Password reset through a one-time recovery code clears the authenticator so a lost device can be recovered; store that recovery code securely. Enabling or disabling the authenticator signs out other sessions.

The top-right avatar opens **Account security**. The sidebar sign-out button asks for confirmation for every role. Use **Refresh** in the top bar to check immediately. While visible, shared reports and area totals refresh about every five minutes; returning to the window refreshes after at least a minute. Hidden tabs do not poll.

On the hosted website, **Account security → Enable alerts** asks for browser notification permission. If enabled, the service worker can show case alerts after the browser tab closes, subject to the browser and operating system allowing background push. Notifications are tied to that signed-in account; signing out removes its registered devices for privacy. The native desktop build continues to use the shared site's in-app notifications. Email alerts are wired to the optional verified email provider and are sent only to verified addresses; they are not live until that provider is configured.

Citizens can see and open only reports they personally submitted, including after those reports are verified or completed. The public issue board is disabled. Administrators and the super administrator can review all reports; assigned department staff can work on their assigned reports. Every signed-in role has a dashboard area search that shows only the **number** of complaints matching an area across all citizens and statuses. It does not return other citizens' report titles, locations, images, or details. Administrators can export a case summary as CSV.

Citizen and completion photos accept PNG, JPEG or WebP files up to 8 MB and are resized and converted to WebP in the browser before submission. The stored image remains below the server's optimized image limit; very detailed photos that cannot fit are rejected with a clear message.

On **Issue map**, a citizen can click within Dhaka to place a new report pin or choose **Use my location** if the device grants location permission. The detected position includes an accuracy estimate and can be corrected by clicking the map. The citizen enters an exact place name or nearby landmark, then selects **Continue to report**; the coordinates and place name carry into the report form. A report is created only after the full form is submitted. The place name is supplied by the citizen and is not independently verified by a geocoder. Selecting a saved map marker zooms to street level and shows its place name, area, status and coordinates. The reporter, administrators, and the assigned department see the exact pin and name. Staff outside that department see only an approximate pin without the place name. Older reports have coordinates but no saved place name; they display “Place name not recorded.”

Report lists load 25 cases at a time. **Load more** requests the next page by case ID; search and status filters run on the server within each role's access. The case drawer loads one report's full detail only when opened. Dashboard counts and analytics are calculated in SQL across all cases visible to the signed-in role. The map adds older points as more pages are loaded, and tells users how many points are currently shown. Indexes cover common report and history lookups.

## Ward queues, private conversation, and reporting drafts

New citizen accounts and reports use a selected Dhaka North (DNCC 1–54) or Dhaka South (DSCC 1–75) ward. Administrators and department staff can open a ward workload card to see that ward's case queue, and filter the complaint list by ward. The server validates ward codes. A new report asks for the citizen's current location and places a pin when permission is granted. The form suggests a ward from approved imported polygons when available; otherwise it uses the bundled reference outlines. It flags points close to a boundary, and the citizen must check and confirm the ward before submission. The issue map bundles 54 North and 75 South ward outlines from the [Dhaka City Corporation polygon layer](https://www.arcgisbd.com/server/rest/services/ADB005/CRIIPS/MapServer/346), with ward identities checked against the [North](https://www.citypopulation.de/en/bangladesh/dhakanorthcity/admin/) and [South](https://www.citypopulation.de/en/bangladesh/dhakasouthcity/admin/) census directories. Select a city to see only its wards and complaints; type or choose a ward to fit and highlight its boundary. The outlines are a visual guide and are not an official land survey. The area-wide count search remains available.

The owner can import approved WGS84 GeoJSON in **Service health & recovery**. Each Feature must have a `properties.ward_code` such as `DNCC-01` and Polygon or MultiPolygon coordinates in longitude, latitude order. The owner records the approving source and date, enters their password, and confirms the import. Importing replacements changes ward suggestions but does not silently rewrite already submitted reports. The current coverage is shown separately for North and South. Do not use the area-list PDF as a polygon source.

The report and registration forms also link to a **2018 DNCC administrative map** supplied by the owner and to the CityPopulation [North](https://www.citypopulation.de/en/bangladesh/dhakanorthcity/admin/) and [South](https://www.citypopulation.de/en/bangladesh/dhakasouthcity/admin/) 2022 census directories. These are visual and ward-name references. The DNCC PDF is a raster map that says it may not be used for legal claims, and the CityPopulation pages list wards and census figures. None of these files or pages provides verified current GeoJSON ward boundaries for GPS lookup. The supplied land surface temperature image shows thermal patterns by locality and is not used to route complaints or calculate the app's issue heatmap.

## Work queue, owner health, and low-data mode

Administrators can assign active cases to staff in the case's department. Department staff can accept an unclaimed case, release their own case, record a blocker, and set the time for their next action. The work queue has unaccepted, mine, blocked, and overdue views. These internal work notes are kept out of citizen case details and timelines. The queue uses server pagination with 25 cases per page and a total count for each filter.

The super administrator's **Service health & recovery** page shows unassigned, unaccepted, blocked, and overdue counts, alert delivery failures from the past seven days, hosted database size, estimated stored image data, and the last manual backup, successful offsite backup, and restore drill. It reminds the owner when no backup generation has been recorded for seven days or no restore drill for 30 days. A manual backup is recorded after the encrypted download is prepared; the owner must still confirm that the file was saved and stored elsewhere. The hosted database size comes from Cloudflare Durable Object storage; local development shows a dash. The backup indicator stays inactive until a private R2 bucket and encryption key are configured. Email verification and password reset stay inactive until a verified sending domain and provider are configured. This page does not claim either service is active merely because the code exists.

**Low-data mode** is a per-device setting in the top bar. It pauses map tiles until requested, loads case photos only when opened, and keeps GPS and keyboard coordinates available for report submission. The owner can select a `.cpbk` backup and enter its passphrase to run an in-memory SQLite data and relationship check without changing the live database. For a full schema restore test, use the local restore script described below.

The administrator, super administrator and department staff dashboards show visible cases within 2 km of their current position after location permission is granted. Location is used for that request and is not saved to the account. A ward filter narrows the nearby list. Dashboard totals, department scorecards, administration counts and ward cards open the corresponding list, detail or section. A department scorecard card filters the area graph when selected.

The super administrator can preview and remove complaints and their related history in **Administration → Remove all complaint records** using the account password and an explicit confirmation. Accounts, departments and categories remain. Download and check a backup first if any records might need to be kept. This tool affects the database to which the app is connected; a local development database and the hosted database are separate.

Each report has a **Private case conversation**. The reporter, administrators, and staff in the assigned department can exchange text and optimized photos there; entries are timestamped and recorded in the case history. A new message creates an in-app notification for the other side. Unassigned departments and other citizens cannot read it. The most recent 200 messages are shown in the case drawer; older messages remain in the database and encrypted backups. Retention and approved citizen data removal scrub conversation text and photos.

The **EN / বাংলা** control on sign-in and the signed-in top bar switches the report form, complaint status, case actions, and in-app notifications between English and Bangla. The language choice is saved to the account for browser push and future email alerts. User-written report text and team notes remain in the language in which they were entered. Email remains inactive on the current site until a provider and sending domain are configured.

The report form guides citizens through **Issue → Location → Photo → Review**. The photo is optional. The final page shows all answers before submission, and Continue never submits a report. Missing information is described beside the relevant field and focus moves there. The form saves its title, description, category, ward, landmark, and pin to this browser or desktop app while the citizen types. It can be reopened after a reload or a temporary connection loss. The form does not submit while offline. A photo is included if device storage allows; if storage is full, the text and pin are kept and the photo may need to be selected again. Drafts are stored per signed-in account on that device, expire after 30 days, and can be deleted from the form. The map and report form also accept latitude and longitude by keyboard, and the mobile smoke test checks the new controls at 390 px and 320 px widths against WCAG 2.2's minimum target size.

Case lists and the case drawer explain the **next step** in plain language. The drawer names the team responsible and shows the target resolution date where applicable; internal staff next-action times remain visible only to staff and administrators. In-progress department staff can choose an editable update template for inspection, materials or work in progress, then post the note to the case timeline. When both the original and completion photos exist, the case drawer shows them side by side with an optional keyboard-operable overlay slider. Citizens should still inspect the real location before confirming a repair.

## Closure targets and recurring issues

Each new complaint gets a **closure target** based on its category. The default is 168 hours (seven days); the super administrator can set any category to 1–720 hours in **Administration → Closure deadlines by category**. Changes apply to new reports only. The target runs from submission until the citizen confirms the completed work. An administrator can see overdue cases in the dashboard and the **Overdue closure** complaint filter. When a case is reopened, a new target starts using the current category limit. Rejected and duplicate reports are excluded. These are internal targets, not official municipal service promises. An hourly Cloudflare job alerts the assigned department as the target approaches and alerts administrators once it passes. Each alert appears in the case timeline and in-app notifications; users who enable browser alerts receive push notifications outside the open tab.

When a new report is submitted, CivicPulse checks for a **closed report in the same category within 100 metres that closed in the previous 90 days**. It flags a possible recurrence for administrator review without merging or rejecting the new complaint. Citizens see only a generic recurrence label on their own report; they cannot see the other reporter's details. Administrators can see the previous case code and title, filter **Recurring issues**, and dismiss a false match with an audit note. This is a proximity suggestion, not proof that the physical fault is identical.

## Citizen confirmation and Finished work

When assigned department staff mark a repair complete, they must add a note and a completion photo. CivicPulse stores the photo, note, and date with that repair cycle alongside the citizen's original evidence, then creates an **in-app notification** for that complaint's citizen. The citizen opens Notifications, checks the work, selects Yes/Partially/No, and rates it from one to five stars. A Yes response moves the case to **Citizen Verified** and stops the closure clock. Only the super administrator can then move it to **Finished work**. A partial or negative response keeps the case awaiting review; an administrator can reopen it for another repair cycle. Each cycle needs fresh citizen feedback. For 14 days after Finished work, the reporting citizen can request rework if the repair fails again. Only the super administrator can approve or decline that request, with a recorded reason; approval reopens the case and starts a new deadline. Notification email is not sent while the site's email service remains unconfigured.

The super administrator has a separate **Finished work** view showing the latest confirmed rating averaged by department, its matching rating count, median hours from submission to citizen confirmation, the percentage confirmed within deadline, the percentage of ever-confirmed cases later reopened, a rework review queue, and a graph of finished cases by area. Legacy Closed cases count in finished-work figures only when the latest repair cycle has a Yes response from the reporter. Ratings from incomplete or disputed work are excluded.

## Connected desktop app (version 0.2.0 and later)

The current E: drive build is **0.11.0**. Install `E:\CivicPulse\CivicPulse Setup 0.11.0.exe`. Older installers are previous releases. The desktop app opens the **same hosted CivicPulse service** as the public website. Citizen reports, department changes, and staff actions are stored in the shared Cloudflare database and appear in website and desktop sessions. Internet access is required. Sign in with an account created on the hosted site; previous desktop-only accounts are separate and will not work automatically.

Previous desktop releases stored data in a private SQLite file on each computer. Installing the new version does **not** upload or erase those files. Reports previously entered in the old desktop app remain local and must be reviewed and submitted again to the shared service by their owner. Do not uninstall or delete local data until those reports have been checked. A department created only in an old desktop release must be created once more by the super administrator in the connected app. Departments are shown in **Administration → Departments**; citizens choose **report categories**, so add or assign a category to a new department before expecting it in the report flow.

For recovery of old desktop records, the code retains a legacy local mode (`CIVICPULSE_LEGACY_LOCAL=1`) that reads the existing local SQLite file without sending it to the hosted site. This is for manual review, not shared operation. The new installer normally launches connected mode.

## Local development web app

Double-click **Start CivicPulse Web.cmd** to open the shared hosted website in your browser. For a separate local development server, run `npm run web:open` from this folder. The local development server opens at [127.0.0.1:4173](http://127.0.0.1:4173/) and saves data in `E:\CivicPulse\data\civicpulse.sqlite`. It is separate from the hosted site and is reachable only from this laptop.

On the first local run, the owner setup form needs the private setup key from `E:\CivicPulse\.dev.vars` (`BOOTSTRAP_KEY=`), plus a name, email, and password. Keep that file private. Existing local demo accounts and sample reports are no longer seeded or used. The former demo database at `E:\CivicPulse\data\civicpulse-web.sqlite` is not loaded by the current app; see the security handoff for its cleanup status.

The normal Electron desktop app is connected to the public service. Local or test mode uses a separate `civicpulse.sqlite` in the Electron user data directory and is enabled only with `CIVICPULSE_LEGACY_LOCAL=1`, the development flag, or the isolated smoke-test flag. If using local mode for first time setup, `CIVICPULSE_SETUP_KEY` can require a setup key.

## Owner backup and recovery

In **Administration → Encrypted owner backup**, enter the owner account password and a separate passphrase of at least 16 characters. The browser downloads a `.cpbk` file containing accounts, password hashes, reports and images, feedback, and audit records. It uses PBKDF2-SHA256 (310,000 iterations) and AES-256-GCM. Keep both the file and passphrase safe, in separate places. Losing the passphrase makes the file unrecoverable. This export is limited to 150 MB of unencrypted data and is assembled in browser memory. It is an on-demand archive; edits made while it is downloading may mean it is not an exact point-in-time snapshot.

The same card can **verify a downloaded `.cpbk` file** with its passphrase. This checks authenticated decryption and required archive structure, then shows account and report counts. A device-local reminder appears if no file has been checked or the last check was more than seven days ago. The owner health page adds a temporary SQLite data restore and relationship check. Neither browser check proves that the production schema can be restored. Periodically run the restore script below into a new local file.

Citizens can request removal of their personal data in **Account security** using their current password. The super administrator reviews pending requests in **Administration**. Approval removes the citizen's account details, case text, photos, precise location and related free-text notes, disables sign-in, and revokes sessions. Case status and aggregate counts remain for service accountability. The owner can also preview and anonymize terminal cases older than 365–3650 days in batches of 50, after entering their password and an explicit confirmation. Active cases are excluded. Previously downloaded backups remain separate copies and must be handled under the owner's retention policy.

To check an archive without writing private records to disk, run `node scripts/restore-backup.cjs E:\path\to\backup.cpbk` from this project folder. The script prompts for the passphrase without echoing it and displays record counts. To restore to a **new local** SQLite file, add a new output path: `node scripts/restore-backup.cjs E:\path\to\backup.cpbk E:\recovery\civicpulse.sqlite`. It refuses to overwrite an existing file and checks SQLite integrity and foreign keys. This does not replace the live Cloudflare database automatically. Test restoration periodically. Never share the decrypted SQLite file or commit it to Git.

Cloudflare also provides [30 days of Point-in-Time Recovery for SQLite-backed Durable Objects](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/). That is the preferred route for an exact live rollback after accidental changes. It must be initiated with a recovery procedure using the Durable Object storage API; this app does not yet offer a live restore button. The code now supports daily AES-256-GCM encrypted snapshots in a private R2 bucket at 18:00 UTC (midnight Dhaka). **They are not active:** Cloudflare currently refuses R2 commands on this account with "Please enable R2 through the Cloudflare Dashboard." The Administration page shows this state. Keep taking manual encrypted backups until R2 is enabled and a daily backup has been downloaded and restored successfully.

To activate R2 later, enable R2 in the Cloudflare Dashboard, create a **private** bucket named `civicpulse-dhaka-backups`, and add `"r2_buckets": [{"binding":"BACKUP_BUCKET","bucket_name":"civicpulse-dhaka-backups"}]` to `wrangler.jsonc`. Generate a random 32-byte base64 key locally and store it in a separate password manager. Set it with `npx wrangler secret put BACKUP_ENCRYPTION_KEY`; never commit the key or paste it in chat. Deploy again. The daily files will be under `civicpulse-dhaka/YYYY-MM-DD.cpr2` in the private bucket. Download one through the R2 Dashboard and verify it with `CIVICPULSE_BACKUP_KEY` set locally: `node scripts/restore-backup.cjs E:\path\to\backup.cpr2`. Add a new SQLite output path to create a checked local restore. Keep the encryption key separately from the bucket. This restores a new local database, not the live site. Offsite snapshots are limited by Worker memory and the script's 200 MB restore cap; monitor failures in Worker logs and keep manual backups if the archive grows.

To activate email later, verify a sending domain with [Resend](https://resend.com/docs/dashboard/domains/introduction). Set Worker secrets `RESEND_API_KEY`, `MAIL_FROM` (for example `CivicPulse <security@your-domain>`), and `PUBLIC_APP_URL` (`https://civicpulse-dhaka.civicpulse-desktop.workers.dev`) using `npx wrangler secret put NAME` for each. Deploy again and test registration, verification, recovery, and alert delivery using addresses you control. Do not enable this with an unverified sender. Email delivery failures are recorded in Worker logs; citizens can request a fresh verification link after one minute.

`node scripts/load-check.cjs` creates 3,000 synthetic reports in an in-memory database and measures 60 local list reads. This is a repeatable pagination regression check, not a production concurrency guarantee; it does not touch the hosted site or real citizen records.

## Security and operating limits

Passwords are salted and hashed; sessions use HTTP only cookies on the hosted site and expire server side. Requests use server enforced role and record access checks, same origin checks, size limits, login and submission rate limits, and security headers. Administrative changes and case actions are recorded in the audit trail. Uploaded images are held in the shared database and are not published to other citizens.

The app has verification and recovery code, but no email provider or domain is configured, so these functions are not live and citizens' email addresses must not be treated as verified. Authenticator sign-in is available to administrator and super administrator accounts, but must be enabled individually. The app cannot guarantee that citizens' free text and images contain no personal details. The owner should review titles before verification and keep Cloudflare account access protected with multi factor authentication. Publish a privacy policy, set a retention schedule, prepare an incident response plan, and arrange an independent security review before inviting the general public to submit sensitive personal information. No deployed app can guarantee zero risk of intrusion or disclosure.

The hosted database currently uses one SQLite backed Durable Object named `dhaka`. Citizen images are stored in that same database, so image growth will consume its capacity sooner than text reports. Cloudflare documents [5 GB total Durable Object storage on Workers Free](https://developers.cloudflare.com/durable-objects/platform/limits/) and [100,000 Worker requests per day on Workers Free](https://developers.cloudflare.com/workers/platform/pricing/). A dashboard left visible makes roughly 24 background API requests per hour for shared reports and area totals, plus occasional page-specific requests. At 150 people viewing it for eight hours each, those two polls account for about 28,800 requests before logins, searches, and actions; monitor real usage and do not treat this as a capacity guarantee. If usage grows substantially, move images to R2 and evaluate a migration from the single object to a database layout suited to higher concurrency. Full CSV export still builds one file per request, and substring search can scan many records; both should be redesigned for very large datasets.

The Dhaka service area is a pilot rectangle (23.65–23.94° N, 90.30–90.54° E), not official municipal boundaries. The report form suggests a ward from the bundled reference outlines when there is no matching approved ward polygon; approved polygons take priority when available. A suggestion can be inaccurate near boundaries, so citizens must check the ward and explicitly confirm it before submitting. The entered place name is not independently verified by an address source. The map uses OpenStreetMap tiles.

When department staff mark work complete, the citizen gets a notification to review it. If the case is still awaiting feedback after two days, an in-app reminder is sent; a final reminder follows after seven days. These are generated by the hosted hourly task and stop when the citizen responds. They do not require an email provider. The interface supports English and Bangla labels, named form controls, a skip-to-content link, and a keyboard confirmation checkbox. Run `npm run smoke:a11y` to check those flows locally.
